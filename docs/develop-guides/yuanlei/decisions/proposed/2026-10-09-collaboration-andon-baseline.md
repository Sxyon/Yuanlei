# 协作任务协议与持久 Andon 整体基线

状态：proposed
类型：architecture
Owner：backend/package/yuxi/delegation/contracts.py

## 问题

现有 Yuxi Run、FIFO、interrupt/resume 和项目权限可复用；元垒委派与结果 Owner 已提供持久意图、回收租约及业务验收。它们尚未形成多连接、任务规则下发、逐级问题返回、持久送达/采用和有限智能体批准。仅增加文本 Adapter 无法覆盖用户的完整协作目标。

## 提案

以 [C0 整体契约基线](../../../../元垒系统架构规划设计/归档/2026-10-10-重整前/第一阶段专项/协作接入-C0整体契约基线与C1-C6验收卡-2026-10-09.md) 为当前推荐，部分取代[局部文本接入提案](2026-10-09-openclaw-text-delegation.md)的开包顺序；协议试验证据和可信输出边界保留。版本任务包显式下发模型可见规则，公共问题协调持久化在元垒，Provider 负责真实执行与可证明回执。

个人连接/目标/执行快照进入 C1；问题、修订、处理节点与有限投递 outbox 进入 C2/C3；补充与结果分开，治理在 C4 校验授权并记录实际 actor。新增持久结构仅进 yuanlei。现有委派/结果、UserInbox、治理服务及 AgentRun 是不同语义 Owner，保持各自事实。

推荐显式处理后继 Run 承担 B/A 处理义务，不要求原委派父 Run 常驻或任意递归子 Run。新处理 Run 仍走现有 FIFO、项目授权与 scope 校验，因果关系由问题处理节点保存；现有子 Run scope 不一致独立修复，不删除 worker 守卫。原生续接未证明时采用准确新尝试，旧问题/答案/输入差异保持可回溯。

## 替代方案

全部交人可减少处理调度，却违反直接上级优先处理与有限批准目标。仅评论/通知无法承担版本匹配及持久责任，可作为明确有限模式。依赖平台内部协作树会使第二渠道无公共历史。扩充任意原生递归需更大 scope/生命周期改动，先实现持久处理后继可收窄风险。通用连接中心、工作流引擎及万能 AI 接口没有首阶段消费者，采用既有注册与窄可选能力。

## 风险

整体机制增加个人连接、尝试及问题投递持久结构与运行调度，成本高于局部 Adapter；分 C1—C6 验收，不能将整体 proposed 视为实现承诺。Multica 部署未知仅阻塞其真实派发，OpenClaw 原生问题/取消/恢复未验仅限制对应动作。个人有限新草案授权需要可机械核查的类型化边界，组织 RBAC、转授权与企业审批链留第三阶段。
