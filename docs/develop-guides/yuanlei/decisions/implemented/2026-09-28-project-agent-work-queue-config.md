# 项目数字员工任务队列配置

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/project_work_execution_service.py
关联 Feature：[独立项目工作任务与 Issue](../../features/project-work-tasks.md)

## 问题

项目任务目前只能由用户逐条接受；派发时才解析模型，期间项目智能体或系统默认模型变化会改变已经接受的任务。工作台缺少每名数字员工的接收策略。

## 决策

在 yuanlei schema v16 的 `project_agents` 绑定上保存 `auto_accept_work` 与可空的 `work_default_model_spec`。关闭自动接受是存量默认值。配置仅影响此项目绑定，不改变普通聊天的 Agent 配置。显式模型必须是当前可用聊天模型；空值表示继承该智能体在项目中的有效模型，若仍为空则继承系统默认模型。

手动任务在接受事务中解析并固化模型；自动模式在分配事务中直接转为 queued，并固化相同模型。配置读写与分配共用绑定行锁，保证一次接受只使用一个版本。固化后模型变更不改写已有执行尝试；worker 仍通过现有 Request/Run 链路最终校验模型可用性。自动接受提交后尝试立即派发，失败由周期收敛器重试。

## 替代方案

- 将设置写入 Agent 基础配置：同一 Agent 在不同项目的工作接收策略无法独立管理，也会影响聊天模型。
- 只在派发时读取默认模型：已接受排队任务会随配置变更改变执行模型。
- 用 JSON 覆盖层保存接收策略：布尔值和模型缺少数据库列约束，也会与聊天 context 覆盖混在一起。

## 后果

存量绑定保持手动接受。迁移前已经接受且 `model_spec` 为空的执行尝试无法还原当时模型，沿原派发逻辑解析；新接受的尝试均固化快照。显式模型在配置时和接受时校验；模型后续停用时，派发保持可观察失败，不静默改用其他模型。工作台可显示当前策略和每次执行的模型快照。
