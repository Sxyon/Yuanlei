# S06原包迁移与当前主题专项收尾

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/project_theme_service.py
关联 Feature：[项目主题](../../features/project-themes.md)

## 问题

S05完成前，主题制作、绑定及真实业务／资料消费已经形成，但正式HTTP版本读取仍返回定义DTO，缺少原ZIP下载与完整导入产品流程。旧S06计划把导入直接登记为发布版，绕开既有“编辑草稿→发布→分配”语义，也没有定义重复、中断、两正式环境和专项退出口径。

## 决策

准确授权版本通过`GET /theme-versions/{id}/package`回读`ThemeStore`中的原ZIP，返回原字节及SHA-256；不从定义DTO重新打包。导出按原来源授权，撤回版本拒绝，停用版本保留既有读取，文件名由服务安全生成。

导入拆成两步：`POST /theme-imports/preflight`只读解析并有界返回format／ABI／基础版本、页面、素材、项目文件alias及原包摘要；`POST /theme-imports`确认时重传实际字节，服务重新解析并核对预检摘要。目标默认新建个人来源草稿，也可写入有权维护的既有来源；既有来源核候选revision，内置来源拒绝。导入只保存草稿，不自动发布、应用或覆盖已发布版。

发布与分配继续使用原不可变版本、来源锁和唯一Project绑定。目标Project的文件alias、Workdir路径、业务身份、generation和会话不进入ZIP；预览复用S05准确引用与临时映射，发布不升级项目，明确分配才改变选择。结果不明时回读有权目录和目标候选digest，只有唯一匹配才定位草稿；不自动重建来源。未新增导入状态表、导入队列、第二套绑定、自动转换或自动发布授权。

恢复意图按确认时最终选择的模式保存：新建个人来源只匹配本次目录之外、名称相同的个人来源；既有来源只匹配准确source及推进后的候选修订。候选回读再次核对digest，核实期间变化则保留输入并要求重新核实。保存／核实返回的准确草稿直接用于定位，避免定位时再次读取另一修订；结束导入清理忙碌状态，使同页连续导入可用。

新建与既有来源共用写后核实：候选提交后回读失败，只有数据库摘要相符且修订已推进时才报告`import_saved_unverified`；保留准确来源供重读。明确的`candidate_conflict`仍直接409拒绝，不能因为当前字节相同就将旧修订请求转换为成功。成功响应前再核对候选digest；提交后被另一窗口替换则返回`import_result_changed`并进入结果核实，不混用本次摘要与其他候选内容。数据库与文件提交点、发布及绑定语义保持。

## 替代方案

- 导入直接登记发布版会绕开草稿、人工预览和显式分配，无法证明“尚未应用”，因此拒绝。
- 在服务端暂存预检结果或引入导入任务表会增加跨请求状态、权限和清理面；改为确认时重传并核对摘要，代价是再次上传和解析。
- 从定义DTO重新打包会改变字节且无法保证与源版本同hash；因此只读写存储中的原ZIP。
- 为文件自动生成占位素材或把源项目路径写入包会掩盖目标缺失；因此保留明确的`file_unbound`和重新绑定。
- 仅凭相同digest自动定位会混淆并发创建的其他来源；保留名称、归属、目录基线和候选修订约束。引入持久导入任务表不属于此次局部恢复修复的必要范围。

## 后果

主题现在具备“A导出原包→B预检→目标草稿→目标资料预览→显式发布→显式分配→重启保持→切回”的完整闭环。用户必须分别确认导入、发布和应用；未编辑的原包在B发布后再导出与A同hash，编辑后则按新内容重新校验和发布。包内作者自行写入的内容仍随包携带，导出不承诺自动脱敏；跨平台适配、自由Vue、模板市场、团队权限和批量升级不在本决策范围。

相关证据由[迁移交接](../../../../元垒系统架构规划设计/图解/33-theme-migration-20261017/README.md)和[主题状态与证据](../../../../元垒系统架构规划设计/LOG-DB-001-Dashboard进度基线与执行记录.md)拥有：

- 真实浏览器35项检查、200次API请求、0页面错误；15项负例覆盖非法ZIP、ABI 4、摘要不符、内置／越权目标、旧revision、同版本异字节、未绑定alias、错误JSON／PNG、缺文件及旧generation；导入响应丢失经显式核实只创建一个来源且未自动发布。
