# 正式工作与业务结果概览

状态：implemented
类型：feature
Owner：backend/package/yuxi/services/inspection_board_service.py

## 问题

督查概览把历史Run失败当作当前阻塞，关系图把建议当作工作；同一工作多个待验收结果与完成状态没有独立口径。

## 决策

授权后只读现有正式工作、结果、尝试、委派及反馈，数据库版本保持 yuanlei=35。默认首页分为待处理、工作进展、待验收、执行异常；分页与计数从同一筛选集合派生，稳定倒序。截止日期按UTC当日判断，done/cancelled不逾期。pending按结果份数和不同工作数分别计数。

每项工作的智能体尝试和委派分别按created_at/id选择最新记录；最新失败/中断且工作非终态为当前异常，其余异常为历史。无正式工作关联的Run保留执行历史，不充当业务受阻。蓝图文件修改时间不推断复盘。

关系图只画现有外键：议题、决策、正式工作、结果，反馈边明确标记。每类最多10条并显示遗漏数量；当前工作关联与来源修订、结果当次冻结来源分开表达，遗漏节点仍提供维护及历史入口。自定义静态Dashboard隔离与现有状态机保持。

统计与分页在一次 service 读取中复用同一集合；repository 只取展示字段，排除资料包、结果正文与事件大对象。URL 从所属项目及记录 ID 生成。详情返回默认概览时重新读取；关闭列表或切换项目后忽略迟到响应。系统规则产生的评论与通知使用“系统规则巡检”，负责人只表达跟进标识。

[督查板只读聚合](2026-09-25-yuanlei-inspection-board.md)中从历史 Run 派生 blockers 的口径和[治理关系图](2026-09-27-project-governance-discussion-and-graph.md)的建议节点由此决定部分取代。原执行读取、工具授权和静态页面隔离继续有效。

## 替代方案

从Run成功推断工作完成会绕过个人验收；保存概览进度或图关系副本会产生双重事实。沿用Owner的只读查询，少量个人数据在服务内同一集合完成统计与分页，避免第二套过滤规则。

## 后果

概览是读取时事实，详情变更后重新读取，不提供实时事件平台。历史异常按两类执行入口分别收敛，不推断它们的执行互相替代。旧执行依据缺失明确显示未知。真实Codex和Multica出向证据保持未验收。

## 验证

聚合与分页的真实 PostgreSQL/HTTP 测试覆盖多结果、已纳入建议、done/cancelled逾期排除、失败后成功、委派远端失败、分页与状态刷新。前端测试覆盖迟到响应、分页重试、正式工作来源、冻结修订、反馈边和图外来源链接。真实页面覆盖四组计数、更多列表、结果定位、详情返回刷新、浅深色与窄屏、自定义静态页保留。实际命令、最终结果与尚未验证范围见[P08执行与验收记录](../../../../元垒系统架构规划设计/归档/2026-10-10-重整前/P08执行与验收记录.md)。
