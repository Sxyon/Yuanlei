## 2. 这轮实质改善

| 检查项 | Dashboard U2 | 协作 C2 |
| --- | --- | --- |
| 是否覆盖整体目标 | 同时覆盖日常九场景与素材、模板、实例、数据、运行时及自主维护 | 覆盖委派、准确身份、交付、补充、求助、返回、采用、授权和故障 |

整体方案与第一阶段方向一致：项目扁平、个人先用、议题/决策/正式工作关系可追溯；跨平台协作复用已有 Owner；组织治理仍第三阶段。有限个人授权可以进入第一阶段，与组织角色系统分开。

## 3. 不阻塞继续，但下一轮要控制的偏差

### 3.1 受控组件不能提前变成永久创作上限

U2 第 5.1 节将 R1 作为主要动态路线，保留 R2 表达力试验，这是合理的起步推荐。但用户原目标包括智能体自主创作项目 Vue Dashboard，不能只用平台熟悉的采购指标验证后，就认定有限组件覆盖未来需求。

U3 应证明两件事：常用业务屏可被智能体组合；项目有不同表达需求时，系统能以有限扩展或隔离代码路线承接。先使用现有采购场景，再选一个结构不同的合成场景或展示要求作小规模压力验证。不要为了使 R1 通过不断增加专属组件或设计通用脚本语言。若验证不足，暂不冻结 R1 为唯一长期方式。

### 3.2 UI 仍未经过视觉与操作验证

U2 的文本线框和关系图已经足以比较职责，但不能解决“界面太丑、重点不直观”的实际问题。U3 主方案需要较完整的可操作界面：排版、留白、层级、密度、状态、主题和关键窄屏行为都要实际呈现，不能只把线框染色。

建议以 A 完成主原型；B 只做高频跨项目办理的对照切片，C 只做业务观察及全屏返回的对照切片。保持相同数据与任务，足以验证取舍；不必把三个候选的九场景都实现成三套完整应用。若对照切片推翻推荐，再扩展相应候选。

### 3.3 试验通过与产品闭环通过继续分开

C2 已正确说明隔离探针不代表现有适配通过。这条区分必须保留到交付：远端可以产出文本，不等于元垒正式工作能从真实入口派发、绑定、回收并生成唯一待验收结果。

T1 先证明协议能力，产品适配完成后再验证真实入口。T3—T7 的持久协议原型同样不能当作已有多级子运行、求助工具或治理批准能力完成。

### 3.4 Andon 解除阻塞不必等整项工作交付

C2 第 6 节要求用后继输出等证明问题消除，适合试验取证。实现时应区分“答案送达、被正确采用、原阻塞条件解除、整项任务完成”。执行者可以已经采用答复并恢复工作，但任务尚未交付。

对不同问题规定可观察的解除依据。例如缺字段已补齐并被对应尝试读取，足以解除该输入阻塞；不能要求每次澄清都等完整最终产物才关闭办理义务。平台只能证明提交时继续显示采用未知，不能为了省步骤伪造确认。

### 3.5 一次授权是验证入口，不是长期自主能力的全部

具体草案授权和预先确定候选集合容易校验，适合第一次验证，但不足以覆盖智能体在委派中提出新方案的目标。有限个人授权后续应至少证明一种有真实 consumer 的授权内新草案变更，范围和副作用由实际 Owner 核验，而不是永远由用户预先批准每份具体内容。

第一批固定元垒项目责任智能体为正式批准主体、不转授，是 C2 的局部建设建议。普通各级执行判断仍按各自委派范围进行；不能误扩成“所有层级只能根智能体判断”或用户已永久否决其他批准主体。

## 4. 下一步按什么顺序推进

两会话可以并行。Dashboard 先验证呈现与操作；协作先完成必要的只读准备。两者交换状态含义和精确对象入口，未实现状态明确作为合成候选，不彼此等待整个专项结束。

| 顺序 | Dashboard | 协作与 Andon |
| --- | --- | --- |
| 下一任务 | U3-A：A 主原型及 B/C 对照切片；默认管理概览、准确办理和业务大屏 | C3-T0：落实真实目标、权限、连接与隔离边界，提交填好的 T1 试验卡 |
| 接续验证 | U3-B：R1 数据/导航/表达力小试验，双项目绑定与草稿/启用/回退模拟 | T1：获具体写入授权后，两平台准确交付；T2 补充可尽量随同一次逻辑委派观察 |
| 再下一步 | 汇总原型证据，分项形成 U4 决定；通过部分可独立规划实现 | 按实际平台证据选择等待或新尝试，再验证单层、多层、人工和限定授权 |
| 独立处理 | 已有办理/导航问题可在相应增量解决，不以模板库为前置 | 第 8 节非终态封存和描述误报止损可另领任务，不等待完整 Andon |

不要一次领命实施所有增量或 T0—T7。也不要重新排一个漫长的讨论前置。下一轮产物应是能操作的原型或能执行的具体试验卡。

文档列出的 120 秒观察窗口与 20k token 是候选，不是用户已经同意的硬预算，也未证明平台能强制执行。T0 由会话核实平台能力、拟定可理解资源范围和一次授权包；不让用户猜 Agent ID 或实现字段。需要外部写入时再针对这份具体试验卡确认，已有明确授权范围内不反复申请。

## 5. 发送给 Dashboard 原会话的下一任务

> 开始 U3 第一轮可操作原型，继承 U2 暂定推荐但不正式定案。以 A 为主完成默认管理概览、稳定项目导航、准确多结果办理和一屏业务大屏的视觉与交互原型；B 只做高频跨项目办理对照，C 只做业务观察/全屏返回对照，不实现三套完整应用。共用合成数据和任务，明确未实现能力。先自行检查层级、密度、主题、窄屏、草稿保持、错误和返回路径，再展示可操作结果及对照依据。技术验证分开做有限 R1 数据/导航样例，并用结构不同的展示要求检验表达力；保留 R2 被证据触发的研究路径，不把受控组件提前冻结为创作上限。原型放隔离产物目录，不接真实业务、不改产品代码、不发布项目 Dashboard。下一轮交付原型入口、同任务对照、关键观察、推荐变化和具体未验项；有完整结果后再讨论少数重要取舍，不继续问局部偏好。

## 6. 发送给协作原会话的下一任务

> 开始 C3 的 T0 准备，仅落实两平台准确交付试验的前置条件。继承 C2，补齐真实调用目标、容器/宿主连接、有效身份与权限、隔离对象、可执行动作、资源范围、停止和清理办法；可从只读发现获得的信息自行核对，不让用户猜 ID 或逐项设计字段。提交填好的 T1 试验卡与推荐，不再复述完整规划，不发真实任务、不改配置或产品代码。初轮明确协议探针与产品入口的不同证明范围；T2 补充能随同一委派观察时并入计划，不额外制造远端动作。远端写入需要针对具体卡的授权，获得覆盖范围后无需每一步再确认。另给一张非终态封存/描述误报止损的小任务卡，保留独立修复路径但本轮不实现。Andon 后续区分答案采用、解除阻塞和任务完成；限定授权先验证具体草案，后续保留授权内新草案能力目标。下一轮应得到可领命执行的试验与缺陷任务，不再进入孤立例子问答。

## 7. 后续审阅标准

Dashboard：必须有可操作界面，能正确辨认项目/工作/结果/要求，核对证据并回原位置；管理与业务大屏相互可达；视觉分层有实际效果；有限组件和自主维护的边界可被观察。

协作：T0 卡已经具体到真实目标和允许动作；T1 真实输入能关联准确 Run 及输出；失败不伪装成功；无真实写入授权不执行，授权内步骤不重复索要许可。后续产品承诺必须补真实入口、持久事实和准确验收的证明。

本轮两个会话不需要重开。下一轮如果回到文档复述、没有原型或未填好的空白试验卡，再纠正任务执行；已有研究方向和事实不用推倒。
