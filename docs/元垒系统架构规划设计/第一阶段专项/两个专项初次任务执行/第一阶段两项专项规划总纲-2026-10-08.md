# 第一阶段两项专项规划总纲

日期：2026-10-08

依据：原系统架构规划、`ef65969` 独立评估，以及用户关于 Dashboard、Multica/OpenClaw、补充汇报、Andon 的补充。

## 1. 专项定位

启动两条持续研究与落地的主线：

1. **信息架构、交互设计与项目 Dashboard 能力专项**：打磨日常工作界面，形成管理仪表板与项目数据大屏的可复用模板、素材和生成机制。
2. **协作接入、过程汇报与 Andon 专项**：用 Multica、本地 OpenClaw 和既有执行入口验证协作契约，建立准确交付、逐级求助与匹配回复能力。

专项不是一次实现工单。每条主线都经过事实调研、问题讨论、多方案比较、原型/协议试验、选择、分批实现、真实使用复评。每轮只承诺本轮能够证明的内容；试验失败可以返回上一轮，不为维持进度掩盖失败。

本文及两个专项文档是规划，不授权直接改产品代码、部署新服务或启动外部任务。研究所需的具体版本、实例、截图和操作样本可在专项中补齐。

## 2. 已明确的方向

| 事项 | 当前确定的方向 |
| --- | --- |
| 项目结构 | 继续扁平；标签/分类区分业务领域 |
| 使用阶段 | 个人先用；组织成员、共享授权、审批链仍第三阶段 |
| Dashboard | 数据展示和分析入口，可进入工作台办理；不是所有维护表单的汇总 |
| 默认仪表板 | 内置管理仪表板兜底，展示议题、决策、工作、结果与异常等真实管理事实 |
| 专属大屏 | 项目智能体依据项目数据生成、维护，可从模板派生 |
| 素材/模板 | 平台提供复用能力；区分内置、个人跨项目共享与项目专属 |
| Dashboard 技术 | 新的 Vue 加载和数据交互机制需要研究并正式定义，不假设已有实现 |
| 协作对象 | Multica 与本地 OpenClaw 均列入真实调研样本；保留现有 Codex/OpenCode 的比较价值 |
| 配置管理 | 共通连接信息统一，协作者专属配置保留差异，不把所有平台套成同一表单 |
| 交付与补充 | 交付物有准确来源；允许补充过程总结、依据、风险和发现，由委派者按需展开 |
| Andon | 直接上级优先结合上下文处理；不能解决才上报；答案逐级返回并准确匹配 |
| 运行和业务 | 运行成功不等于验收通过；执行处理意见不自动成为正式治理决策；明确授权下可批准部分正式变更 |

“共享模板”在第一阶段首先解释为同一个人跨项目复用，以及平台提供的内置模板。跨用户/团队发布与授权是未来扩展；共享可复用结构不得顺带共享原项目数据与凭据。

## 3. 已补充确认的授权边界

用户已明确选择：**允许在用户明确授权后，由智能体批准部分正式决策变更。**

据此专项必须同时覆盖两种行为：在本次委派范围内解答/调整执行；依据明确授权批准限定范围的正式决策变更。后者不能仅靠 prompt 自称获授权，应能核查授权人、范围、有效期限或适用执行、资源上限及是否可再委派，保留实际决策者与授权依据。具体授权表达在专项中研究，不在此冻结数据库字段。

授权不自动向所有子任务扩散，不自动扩大范围；越界、授权失效或正式变更与当前版本冲突时继续上报。未获这类授权的智能体只能提出正式决策变更建议。正常的执行答复仍不应全部升级成正式治理 Decision。

该答复已消除启动前的核心歧义，可以开始两条专项的研究轮。后续影响数据、执行权限和发布行为的具体方案，在各自定案轮再确认。

其余细节留在专项内逐轮讨论：模板具体存储、Vue 渲染方案、发布模式、库界面、OpenClaw 部署参数、补充内容分类、求助时限、取消传播等，都不需要现在一口气问完。

## 4. 两专项共享的设计基准

先研究一组具体场景，而不是先建立组件清单和抽象框架：

- 普通人工事项：独立创建、人工交付、接受，不强制建议题或配智能体。
- 管理仪表板：看到待验收结果，进入准确结果位置，核对文件并作判断。
- 项目数据大屏：项目数据变化后可刷新；看得出来源与时间；没有数据时不编造数字。
- 多层协作：项目智能体委派子任务，子任务遇到歧义，由直接委派者解答后继续。
- 跨平台求助：远端发现缺资料，本地上级补充；越出其权限后继续上报。
- 人工介入：多层智能体都无法处理，用户补充后，答复沿原问题链返回并恢复正确尝试。
- 历史变更：旧答案晚到、任务已取消或已重新运行，不能错误恢复新的尝试。

两专项共同维护场景编号和术语解释，但不建立另一套可以独立修改业务事实的中央状态系统。

## 5. 轮次而非一次任务

| 轮次 | 主要目的 | 可审阅产出 | 推进条件 |
| --- | --- | --- | --- |
| 事实轮 | 看现有代码、真实页面与实际协议，补齐部署版本 | 现状图、问题证据、能力矩阵、未知项 | 能区分已实现、可用、假设与缺失 |
| 定义轮 | 确认用户场景、概念和边界 | 场景脚本、术语、状态含义、必须保留的不变量 | 核心歧义消除，剩余细节明确归属 |
| 比较轮 | 对照 GitHub/官方资料研究可行路径 | 多方案、场景对照、具体取舍及淘汰理由 | 没有预设唯一方案，不以模式或截图数量证明价值 |
| 试验轮 | 用原型或隔离协议试验检验最不确定的部分 | 可操作原型、真实回读、失败记录 | 关键能力有证据，不能实现的能力明确降范围 |
| 定案轮 | 形成当前版本的方案与接口契约 | 设计文档、决策记录、兼容/迁移边界 | 用户能审阅具体方案，再确认影响范围 |
| 实现轮 | 拆成可独立交付的增量 | 代码、测试、真实页面/渠道证据 | 每次修改不破坏既有闭环和历史 |
| 使用轮 | 实际工作中复评，再迭代 | 操作卡点、证据、下一版调整理由 | 不因一次验收而宣布专项永久结束 |

轮次可回退和重复，不按固定日期强迫定案。不能把比较轮和试验轮压缩成“选个库然后直接开发”。

## 6. 并行关系与范围控制

两专项可以分别研究，但应在以下地方交换结论：

- Dashboard 怎样表达协作进展、求助和待验收；哪些只呈现摘要，哪些引导进入工作详情。
- 协作层实际能够提供哪些状态和补充内容；不能为满足原型虚构远端能力。
- 配置与执行准备怎样呈现，不把所有提供者配置放上工作首屏。
- 读数据、发起操作、生成草稿和正式发布的边界一致。

已发现的提前回收、结果描述冒充输出、人工巡检误判和日期不一致仍需关闭。修复可作为专项事实和落地中的小范围工作，但不能等到整套视觉/框架完成才处理；也不能将单个修复当成专项完成。

不包含：周期业务引擎、组织架构、团队访问控制、通用工作流编排、组件市场、任意插件热加载、所有 AI 服务的统一运行底座。

- 事实调研与外部版本记录，正文链接到支持结论的资料。
- 每轮讨论结论与实际取舍，避免把聊天全文当设计。
- 多方案比较及被否决理由。
- 原型/协议证据与未验证范围。

具体数据库表、HTTP 路由、Vue 组件结构、适配器类等在方案定案后再形成实现计划。现在只约束它们必须服务的业务含义，不冻结未经验证的实现。
