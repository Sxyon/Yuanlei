# DEV-MG-001｜专项推进与设计汇报机制

本机制面向用户、执行者和独立Reviewer，负责专项设计、范围确认、开发交付及验收。需求由SYS拥有，实施约束由DEV拥有，状态、用户确认和证据由LOG拥有。测试命令、贡献及文档规则分别由仓库开发规范维护。

## 接入与职责

专项开始先读根AGENTS、当前子树AGENTS、[本目录入口](README.md)及对应SYS／DEV／LOG，读取源码重建实际状态。暂停专项保持暂停；当前文档调整只授权管理资料整理。

开始汇报压缩为可验证的目标、非目标、验收主张及简短步骤，每步说明验证方式。已有明确授权继续有效；技术细节由执行者选择并解释。假设显式记录后推进；解释差异会改变验收、数据、安全或外部状态时，列候选与推荐集中澄清。

Codex负责问题分析、整体设计、取舍、图稿／原型、实现与自检；用户判断关键产品方向与边界。用户走查用于产品反馈，执行者先把方案和证据整理成可评判结果。

## 设计与确认

设计稿标明版本、当前阶段及上下文，按“整体位置→模块理念→关键状态→替代与推荐”组织。每个模块说明解决什么、默认看什么、操作准确对象、依赖、返回、权限、历史及空错。页面布局用草图或原型；涉及架构／关系／流程／状态的取舍时使用Archify，关系未变复用有效图。图稿按技能保留candidate、校验HTML和回执，自动检查与目视审阅分别报告。

调研和小试先于技术定案，只细化当前阶段及必要近端依赖。远期保留目标、未知和验证时机。可逆隔离稿及独立已授权工作可以继续；新的核心路线、页面组织、权限或范围变化先给完整可审材料。用户明确要求直接实现时按该范围继续。

LOG记录原用户消息日期／会话定位、准确稿版本及确认范围。Agent建议、Reviewer通过、原型点击、测试绿色和无回复均不扩张确认。局部确认只适用于其范围；改变SYS目标先说明产品损失、增量、代价与推荐，再同步SYS／DEV。

关键假设失败、需要扩权、兼容或迁移失效、成本显著改变或用户提出新方向时中断受影响路径，交事实、替代和恢复条件。无依赖且已授权工作继续。

## 汇报与交付

日常汇报用进度、问题、下一步；关键选型用现状、问题、真实替代、推荐和待判断点。每轮先说明目标落实、正常产品入口和可见影响，再给语义Owner、实际证据、失败与未验。最终答复自包含核心结论和准确文件入口。

| 状态 | 必须交付的内容 | 下一步依据 |
| --- | --- | --- |
| 开发与相关自检 | 当前范围实现、相关检查、正常入口及未验 | 可运行且范围清楚 |
| 待人工验证 | 简短变动；入口→操作→可观察结果；少量关键错误／空态／返回；代码与主题版本 | 用户反馈或明确验收 |
| 反馈修正 | 原问题、修正和代表复验路径 | 意见解决并获明确人工验收 |
| 验收后全量 | 按[测试规范](../develop-guides/testing-guidelines.md#专项人工验收与全量测试时序)执行，登记命令、失败及剩余范围 | 相应全量通过 |
| 最终收尾 | 人工依据、全量结果、交接版本及仍暂停范围 | 按授权提交或交接 |

本时序依据用户2026-10-16要求。验收前只做相关检查与必要工程／文档gate；未执行全量保持未执行，CI和guard继续生效。纯文档整理执行文档检查，无需虚构产品人工测试。原命令、结果和精确过程可由Git追溯，当前LOG维护状态摘要与直接证据，删除已吸收的重复过程。

## 独立Review与验收原则

全新Reviewer不继承开发上下文，核对完整需求、确认范围、源码、diff、测试、图稿及未验。以下情况退回修正：范围或确认依据缺失；擅自恢复暂停任务；目标损失被局部稿覆盖；缺真实消费者或小试就锁定远期机制；证据只靠作者报告、HTTP200、模拟调用或截图；缺持久事实与必要负例；未人工验收先跑专项全量，或把待验写成最终完成。

产品验收从正常导航开始，读写、历史、错误及恢复覆盖同一目标。主题必须覆盖完整项目界面及办理，原业务Owner指后端事实、权限、状态和审计；已批准界面与实际产品逐模块对照。准确结果的标题、摘要、验收条件、文件及办理可取得，首屏信息按需分层。主题显示名、Run终态、业务接受和目标完成各自判定。

Reviewer与结构gate分别负责语义审查和可执行检查，不能代用户批准设计、审美或业务验收。人可问责Review负责阻止范围和证据失真。
