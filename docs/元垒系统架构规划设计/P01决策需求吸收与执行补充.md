## 2. 逐项判断

### 疑问一：待审核议题新增决策就已实施

判断正确，保留。

需要拆开两个问题：新建不应自动批准；批准不等于已实施。待纳入只是议题是否进入管理范围，不是组织审批门禁，不能进一步推导“待纳入时绝对不能做正式决定”。

P01默认创建草案，明确点击批准才生成拍板事实。可提供清楚命名的“保存并批准”短路径，但不能普通保存后暗中批准。待纳入或拒绝纳入时提示议题状态，由个人用户明确选择；不要求先增加团队审批流程。

旧implemented映射为approved，只承认已有拍板，不推断现实已经落地，也不批量降回草案。旧proposed映射draft。

### 疑问二：确认前可改可删，确认后错误却不能修正

诉求成立，但“批准后不能直接覆盖”和“批准后不能纠错”不同。

| 情况 | 正确操作 | 历史处理 |
|---|---|---|
| 草案修改 | 编辑，检测并发版本 | 保存局部修订 |
| 无引用草案误建 | 删除，首期软删除 | 保留内部历史与来源，不提供永久销毁 |
| 草案已有受保护引用 | 阻止删除，先解除可解除引用或保留 | 防止历史依据失联 |
| 批准文本错字，不改变意思 | 追加勘误 | 原批准文字保留，同时显示更正 |
| 数字、范围、条件或实际选择写错 | 新决策替代或补充 | 即使原因是手误，也有业务含义变化 |
| 已批准决定不再执行 | 撤销并记录原因 | 保留批准和撤销事实 |

例如“每周周报”误写成“每周周抱”可勘误；“预算5000”误写成“预算50000”必须重新明确决定，不能当成普通错字覆盖。

勘误首期只保存字段、原片段、更正片段、原因、操作者和时间。页面展示原文及更正注释，不自动拼出新的权威结论；有争议时按新决策处理。当前个人用户判断是否改变业务含义，系统不依赖AI自动判断，也不建立勘误审批组织。

### 疑问三：共识、补充、替换与完整时间线

大部分有价值，需调整表达。

1. 共识可能只是讨论总结。明确批准并愿意以其指导行动后，才是正式决策。不能按讨论发生在议题结束前还是执行中决定效力。
2. 补充和替代需要真实目标关联，tag只能帮助展示，不能决定谁被替代、哪些结论仍有效。
3. 普通、补充、替代是形成方式；草案、已批准、已被替代、已撤销是状态。勘误是更正记录。三个维度不能混成单一状态或自由标签。
4. 里程碑和大事记只借用时间线呈现方式，不新增管理模块。重大节点突出，修订细节可展开。

## 3. P01最小模型与行为

### 3.1 决策关系

首期最多关联一条目标决策：

- 普通：独立决策，不要求目标。
- 补充：明确`补充哪条决策`；新草案批准后追加要求，原决策保持已批准。
- 替代：明确`替代哪条决策`；新草案批准时旧决策变为已被替代。

可采用关系类型和目标字段，不同时建立自由tag、类型字段、通用图关系三套可编辑事实。形成方式在批准后不改写。

目标和新决策必须属于同项目。关联议题可以不同，但界面明确来源；若首期页面只支持同议题，则明确这一产品限制，不假装数据库已经支持所有跨议题关系。批准关联操作必须重新校验目标当前状态，不仅创建草案时校验。

首期支持整条替代，不支持一条新决策同时替代多条旧决策。调整原决策的一部分时，新决策重述需要继续生效的完整内容，再整条替代，避免隐藏的半失效内容。

补充不能偷偷否定原结论。有矛盾时应使用替代；多条有效决策仍允许存在。原决策被替代或撤销时，相关补充醒目标记“原依据已变化，需复核”；保留其现有状态，由用户明确处理，不自动撤销补充或任务。

### 3.2 修订与时间线

决策局部保存草案版本和生命周期事件，复用已有工程模式，不泛化为全系统事件平台。

记录创建、草案修订、批准、勘误、补充批准、替代批准、撤销、删除；节点保留时间、操作者、原因及相关决策/版本。批准锁定正文和依据版本。旧数据建立迁移基线，未知编辑历史不能补造。

决策详情展示完整局部历史；议题时间线增加同事务写入的决策关联节点。原批准、替代来源和新结论可点击互相定位。事件只作为历史，当前状态由决策对象拥有，不能让两套状态各自可编辑。

草案保存与批准竞争时按版本和行锁校验，批准成功后旧草案保存必须失败。替代批准锁定目标，保证两个替代草案不能同时成为该决策的直接有效替代者。相同批准重试不重复事件。

### 3.3 旧流程联动

- 议题“确认已形成决策”只能选择当前已批准关联决策，排除撤销和替代记录。
- 确认研讨进度仍为显式操作；新建或批准不自动关闭议题。
- 暂停提示仍独立，新增决策不会自动清除；通过现有显式确认操作清除时，界面明确说明。
- 关联任务/Run不自动暂停，不重定向历史来源。
- P02尚未建设时，只展示当前已有任务引用，不在P01顺手扩张正式工作关系。
- 创建和批准都检查议题当前归档/删除状态；历史决策即使议题归档仍可读。若需撤销历史决策，不应因归档而禁止所有独立决策治理操作，具体锁和接口需区分新建关联与历史处置。

## 4. 页面设计

```text
决策：标题      草案 / 已批准 / 已被替代 / 已撤销
形成方式：普通 / 补充某决策 / 替代某决策
结论、理由、依据议题版本
原批准文字（有勘误时显示更正标记及说明）

草案：[编辑] [批准] [删除]
已批准：[补充] [调整并替代] [记录文字勘误] [撤销]
历史：[查看原决策] [查看后续决策]

重大变化（最新在前）
  新决策批准并替代 → 新旧结论与原因
  补充批准 → 原决策保持有效
  文字勘误 → 原片段与更正
  原决策批准 → 当时完整正文及依据
  草案修改 → 展开查看版本
```

批准、替代和撤销使用具体动作按钮，不以一个普通“保存”承担所有效果。替代确认展示旧/新结论与影响提示，不引入强制团队审批。

## 5. P01内部交付顺序

1. 先完成草案编辑/删除、明确批准、旧状态迁移、批准原文和局部历史。
2. 再完成补充、整条替代、撤销、文字勘误和引用保护。
3. 最后更新议题确认、当前/历史决策展示、图与督查标签，验证并发、旧数据和真实页面。

三个步骤属于P01同一需求，可拆成可审查提交；P01全部验收后进入P02。无需重做P00已完成的状态设计。

## 6. 新增验收项

- 普通新增默认草案，待纳入时不暗中批准；显式批准才生成拍板记录。
- 草案能改，无受保护引用能删；批准后编辑接口拒绝覆盖。
- 文字勘误可查看原片段、更正、原因和时间；数值/范围变化走新决策，不覆写原文。
- 补充草案无正式效力；批准后原决策仍有效。
- 替代草案不改变原决策；批准时新旧状态同事务变化，双击/并发不会双重替代。
- 撤销不删除历史，不自动停止任务和运行。
- 来源决策失效的补充能看到复核提示，不自动被当作新的有效整体方案。
- 已形成决策候选排除被替代/撤销记录；新批准不自动改议题进度或清除暂停提示。
- 历史旧implemented映射为已批准，不被当作已落地；未知修订保持未知。
- 当前与历史决策、勘误、补充和替代可在真实界面互相追溯。
