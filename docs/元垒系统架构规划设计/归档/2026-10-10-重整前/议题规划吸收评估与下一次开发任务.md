## 1. 判断

原会话的核心诉求仍然成立：议题是持续维护的业务对象，实践反馈可以改变理解，同一议题应保存讨论与修订脉络。它能补充总规划中较粗的议题设计，不需要推翻整个原任务。

需要调整的是旧会话建议的单一状态机：“研讨中、已通过、已拒绝、已达成、已终止”混合了纳入审核、讨论进度、实际结果与停止推进。按这一状态机继续开发，会重新混淆总规划已拆开的边界。

推荐继续原本地会话，先用新的交接范围替换未完成的状态机设计。下一次切入点就是议题生命周期与修订时间线；不必按路线图顺序先开发项目分类或蓝图模板，它们不是该工作的依赖。

## 2. 原会话的确认状态

根据用户提供的会话文本，已经明确回答的内容：

- 议题同时支持问题型事项和带目标的推进事项。
- “已达成”指实际目标实现。
- 普通研讨持续可用；通过前后的讨论靠时间线节点区分。
- 讨论类型保留研讨、重议、纠偏，不新增决策讨论类型。
- 正式重开时明确继续或暂停原方案；暂停仅为议题层记录与醒目提示，不控制关联任务。

初始诉求还明确要求归档、删除、修改、拒绝后复议、历史快照、倒序时间线、回复和采纳表达。

尚未回答的第二轮建议包括：新增终止状态、修改时选择直接生效或重审、达成说明的具体规则、修改与重新提交是否分开。不能将旧助手的倾向选项当成已批准需求。

## 3. 逐项吸收与调整

| 旧诉求或建议 | 判断 | 新规划中的处理 |
|---|---|---|
| 同一议题持续维护 | 直接吸收 | 稳定身份；拒绝、复议、修订保留在同一对象 |
| 通过后仍可讨论和修改 | 直接吸收，明确依据边界 | 纳入不锁死研讨；修改正文不覆盖已批准决策 |
| 已拒绝也能改、讨论、复议 | 直接吸收 | 修改和重新提交分开，保留拒绝理由和历史 |
| 研讨、重议、纠偏 | 直接吸收 | 默认研讨；类型只是意图，不自动触发重开或撤销 |
| 重开时继续或暂停原方案 | 吸收并收紧语义 | 保存业务提示；不暂停任务、Run，不撤销决策 |
| 增加已达成状态 | 保留业务需求，调整模型 | 可选结果确认及证据；不作为单一议题生命周期状态 |
| 新增已终止状态 | 暂不吸收单一状态 | 议题可关闭并记录不再推进的原因；停止工作另行维护；正式决定撤销通过决策处理 |
| 修改历史与旧描述快照 | 提升为第一阶段局部能力 | 专用最小修订记录及时间线；通用版本平台仍暂缓 |
| 当前描述置顶、历史倒序 | 直接吸收 | 当前内容与倒序时间线分区；稳定排序与分页避免丢失历史 |
| 评论回复与采纳标记 | 保留，分批实施 | 第二批一层回复和独立处置；不开发复杂论证图 |
| 有价值归档、无价值删除 | 吸收，补引用规则 | 归档可恢复；有业务引用不能删；无引用首期软删除 |
| 修改时选择补充或重新审核 | 调整 | 内容修订与议题重开可以组合操作；不重新审核纳入资格，不自动替换正式决策 |

最重要的反哺：总规划原本暂缓“完整议题版本系统”，但持续修改和历史讨论已经是明确需求，因此第一阶段需要最小快照。建设范围限定在议题，不扩大成全系统事件溯源或版本框架。

## 4. 下一次开发任务范围

建议任务名：**议题持续研讨与修订历史：拆分纳入和进度，支持重开及归档**。

### 4.1 第一批：形成完整、可用的小闭环

1. 将纳入状态与议题进度分开，继续保留来源归一、审核责任与去重约束。
2. 已纳入和已拒绝议题可修改及讨论，提供显式重新提交与重开。
3. 支持研讨、重议、纠偏类型，默认研讨；增加讨论不改变状态。
4. 标题和正文修订保存快照；讨论关联当时版本；生命周期操作形成时间线节点。
5. 当前内容置顶；时间线倒序，展示节点、操作者、原因及可展开的历史正文。
6. 重开保存继续／建议暂停提示；明确不改变关联工作和运行。
7. 支持归档、恢复；无受保护引用时软删除。有引用时给出具体拒绝原因及归档入口。
8. 联动修正项目 Dashboard、督查板、议题选择器和图展示的状态判断，防止新状态使其他页面漏数据。

这一批不要求修改完整决策生命周期。通过显式提示明确“议题纳入不等于决策批准”，批准记录的语义纠正和替代／撤销作为紧接着的独立工作包。第一批必须保证议题修订不会改变已有决策正文或运行输入。

### 4.2 第二批：结果确认与讨论处置

在第一批闭环完成后，补充可选目标描述、实际结果确认及证据，一层回复和采纳／部分采纳／不采纳处置。结果确认与研讨状态分开；问题型议题无须填目标。采纳记录关联实际修订或决策，无修改对应时允许说明，不能伪造采纳去向。

第二批可以继续在同一会话推进，但应形成独立可验收变更，避免第一批夹带完整目标模块。

### 4.3 本次非目标

团队与权限、组织审批人、全局目标中心、独立 Proposal、Work Definition 周期引擎、Context Pack 完整实现、通用事件／图引擎、任务自动暂停、Run 取消、完整决策替代系统、无限层级回复、永久删除清理。

## 6. 状态迁移与历史规则

旧 proposed/canonical/rejected 保留对应纳入语义。原数据没有表达研讨是否结束，不能把 canonical 自动推断为“已形成决策”“目标达成”或“已关闭”。建议历史议题进度默认开放，并记录迁移来源；是否存在明确可用依据需在本地核对。

迁移建立当前内容的基线修订，标明它是迁移时快照。已有评论、审核时间和作者保留；过去没有保存的正文版本不能重建，也不能把旧评论伪装成当时已绑定准确版本。旧评论应允许版本未知。

修订、评论、状态事件使用同一议题行锁或等价串行机制。正文更新与快照／时间线事件同事务提交；并发编辑应通过预期修订号或等价方式检测冲突，避免覆盖他人的修改。

归档、删除不级联销毁引用。引用检查覆盖决策、两类任务、执行依据以及本次实际新增引用。软删除只是隐藏和保护历史，不意味着彻底清除数据。

## 7. 必须验证的验收场景

- 议题纳入后仍可追加研讨、重议、纠偏；拒绝后可修改、讨论和显式重新提交，ID 不变。
- 一条重议评论不会自动重开；重开不会自动撤销决策。
- 修改当前正文后，旧修订及关联讨论仍可读取；并发修改不静默丢失。
- 重开选择建议暂停，页面醒目显示；关联任务、Request、Run 状态不被改变。
- 归档后退出默认活跃列表，能恢复；历史引用仍能定位。
- 有受保护引用的议题不能删除；无引用误建议题可软删除，不出现在新工作选择器中。
- 时间线倒序且稳定，迁移基线与真实旧事件区分，未知历史不被编造。
- 来源渠道唯一性、审核记录、当前用户归属与后端访问限制保持。
- Dashboard、督查板和工作议题选择读取相同状态含义，归档展示规则一致。
