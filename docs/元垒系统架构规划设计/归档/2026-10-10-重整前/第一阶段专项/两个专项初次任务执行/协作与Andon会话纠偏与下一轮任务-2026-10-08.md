## 3. 既定产品目标直接继承

- 个人先用、项目扁平；组织架构、团队角色、企业审批链留第三阶段。
- Multica 与本地 OpenClaw 都是实际样本，现有执行入口也是比较基线。
- 连接信息可统一管理，专属配置保留差异，不把所有协作者套成同一表单。
- 委派需要准确执行者和运行身份，真实交付与业务验收分开。
- 交付外允许过程摘要、依据、发现和风险等补充，由委派者按需读；关键阻塞不能藏在可选补充里。
- Andon 由直接委派者先结合自身信息和权限处理，需要时逐级上报，答案沿对应问题链返回。不能只透传给人，也不能上报后丢失。
- 用户明确授权后，智能体可以批准部分正式决策变更；授权必须可核查，实际批准者必须可追溯。

现阶段限定个人授权可以建设，不等于前置完整组织权限系统。提示词、自称授权或父级身份不能替代授权事实。

## 4. 本轮先解释完整协作闭环

用具体场景画出以下路径，列出输入、状态、责任方、事实存储、远端能力和失败结果。图中清楚标明已实现、候选和未验，不把规划画成当前机制。

委派者明确目标及依据 → 选择连接和协作者 → 派发及获得准确运行映射 → 观察 → 接收正式交付和可选补充 → 本地办理验收。

过程中产生问题 → 直接委派者处理 → 必要时升级 → 上级答复或形成授权内正式变更 → 逐级返回适用答复 → 送达 → 执行采用和恢复 → 问题解决；异常时保留待处理入口。

| 场景 | 必须说明 |
| --- | --- |
| 正常交付与补充 | 取得的是当次输出而非 issue 描述；文件与补充准确绑定本次运行 |
| 直接上级解答 | 有明确批准资料且在执行范围内时自行答复，不重复问用户原则 |
| 两级以上处理 | 一层不能处理时附必要上下文上报；各层获得结论后如何转成其下级可执行输入 |
| 用户介入 | 哪些问题真正进入人的待办，回答如何回到原等待尝试 |
| 授权正式变更 | 如何校验明确授权及决策版本、保留历史、显式采用新依据 |
| 不支持原运行续接 | 怎样采用明确的新尝试，保留旧尝试和问题关系，怎样向用户说明限制 |
| 并发与晚到 | 相似问题不串线；取消、更换尝试和旧答案不错误恢复新执行 |
| 重启或父 Run 结束 | 谁继续处理，如何持久送达、去重及判断已经采用 |

例子必须标前提：“三年”是正式批准约束才可能需要正式变更，是执行暂定方法则按委派范围处理；不能从一个数字变化自动推出治理审批。

## 5. 补齐事实对方案的影响

将未知项分成：可以带假设继续研究；试验前必须补齐；形成产品承诺前必须证明。每项附验证办法、影响的具体推荐和不成立时的退路，不只列“待确认”。

Multica 重点核对实际服务可用的派发、执行者指定、触发关联、task-run、当次消息/结果/文件、等待与答复入口、取消和回读。不要用参考版本的存在性推断实际接口一定支持，也不要仅因尚未取得完整 SHA 就停止所有比较。

OpenClaw 重点核对实际版本的 Gateway 与受控 CLI 路径、目标身份、session/Run、输出、事件、等待/答复和恢复；核对容器到宿主连接及最小必要权限的实际成本。本轮只读；真实执行证明留隔离试验。

针对能力缺失，比较受支持的原生行为、受控新尝试、仅通知或不提供该动作。不得通过改本地状态声称远端已停或已恢复，不扫描私有 transcript 充当长期稳定协议，也不为补接口先 fork 改造远端平台。

## 6. 分层比较并给出推荐组合

不同层可以分别选择，不绑成一个只能整体接受的方案，也不为凑三套方案制造劣质替代。

| 层 | 比较内容 | 必须给出的判断 |
| --- | --- | --- |
| 连接与配置 | 提供者、连接实例、目标、当次生效配置；远端拥有长期配置或本地有限管理 | 哪些共通字段现在必需，哪些只记录或引用，如何避免完整配置平台 |
| Multica 接入 | 独立委派工作项与复用已有工作项；明确目标与平台分派；如何证明触发和 Run 归属 | 当前最可靠的起步路径、兼容成本及不能承诺的行为 |
| OpenClaw 接入 | Gateway 原生与受控 CLI；必要时说明有限过渡组合 | 运行身份、交互、最小权限、事件及恢复成本的比较和推荐 |
| 交付与补充 | 稳定公共摘要/引用和提供者扩展；内容持久位置与按需读取 | 最小必需内容，真实来源与执行者自述怎样区分 |
| Andon 协调 | 元垒持久协调与平台原生协作的职责分工；纯评论/通知模式作为有限替代 | 谁拥有问题、转交、答复、送达和恢复事实，平台不能提供的能力怎样呈现 |
| 限定授权 | 单问题/草案的一次授权；项目/类别/期限内有限授权；用户直接批准作为缺授权退路 | 操作频率、可核查范围、撤销/并发成本和分批采用顺序 |

可用以下暂定建议作为研究起点，需由证据支持或推翻，不视为我已拍板：复用现有委派与结果 Owner；元垒保存跨平台问题和处理链，平台原生能力负责其真实执行；远端长期配置优先仍由远端管理；先验证具体一次正式变更授权，再扩展到能明确核查范围的有限授权。

限定授权的推荐不能永久缩成“全部由人批准”。一次授权与有限授权可以是建设顺序，而不是互斥选择。撤权、过期、超范围、旧版本和重复动作由真实副作用边界校验。

设计模式用于解释职责分离和复用理由。已有注册、Adapter 和窄接口足够时直接复用；不要为展示 Bridge、Factory、Strategy 建立多个没有实际消费者的类或万能 AI 接口。

## 7. 为已知缺陷保留独立处置路径

当前回收按钮终态不一致、提前封存 reclaimed、原描述冒充结果和缺少准确远端 Run 绑定必须进入方案。区分可独立修复的状态/封存问题与需要真实能力试验的输出归属问题。

提交每项缺陷的当前失败路径、现有 Owner、最小修复边界、回归验证及是否依赖新接入方案。不要仅写“到 C5 处理”，也不要未经本次范围授权直接修改代码。无需等完整框架定案的修复可以作为单独、可领命执行的后续任务。

## 8. 推荐之后提交试验与建设安排

把本轮推荐拆成模块增量，说明先后依赖、实现约束和可观察验收。至少回答：先证明准确交付，还是先造求助全树；第二个平台何时用来验证抽象；哪些最小个人授权能力进入第一阶段，哪些组织治理留第三阶段。

下一轮隔离试验计划需要具体说明：所用版本和连接、协作者与隔离对象、输入/预期交付、真实写入范围、允许执行动作、运行与问题关联、最终回读证据、失败停止条件，以及重试与清理安排。授权尚未明确的实际动作标清后续确认，不发出任务。

试验按风险逐层增加：单次准确交付；可选补充；直接上级处理；逐级上报与返回；用户介入；授权内正式变更与越界拒绝；重启、并发和晚到。各平台只承诺已证明部分，无法支持的原运行恢复可以研究准确的新尝试替代，明确不同语义。

与 Dashboard 专项交换可呈现的状态、补充及准确办理入口：当前谁处理、是否需要人、答复是否送达、是否恢复。实际还没有的能力可以作为标注候选用于原型，不能伪造运行事实。
