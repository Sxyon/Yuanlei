### 2.4 新增必验项：平台外壳与项目 Dashboard 的嵌入联动

Dashboard 属于项目，元垒属于平台。当前原型中的项目侧栏不能直接当作完整平台侧栏的替代，也不能在真实产品中把两套宽侧栏直接叠加。后续必须同时展示平台全局导航、项目内管理入口及 Dashboard 内容组织，并明确每组入口的职责。

```mermaid
flowchart LR
    P[平台外壳：全局入口与跨项目切换] --> S[项目工作空间：当前项目与管理入口]
    S --> D[项目 Dashboard：管理概览或业务大屏]
    D --> W[准确工作与结果办理]
    W --> D
```

平台外壳拥有自己的导航、折叠偏好和全屏退出入口；项目工作空间拥有项目身份及工作台、治理、工作、智能体、资料等入口；大屏可以拥有业务筛选、图层或自己的内容导航，但不需要每个模板都复制一套项目管理菜单。即使视觉上合并导航，也必须说明当前入口属于哪一范围。

用户提出的两个方向作用于不同层，可组合比较，当前均为候选：

| 候选 | 作用和收益 | 代价及必须验证的问题 |
| --- | --- | --- |
| 进入项目 Dashboard 后平台导航自动收起，悬浮展开 | 为项目内容腾出横向空间，保留全局出口 | 入口发现、误触和遮挡；鼠标离开不能使键盘焦点或正在操作的弹出菜单丢失；触屏需要点击入口 |
| 项目导航可折叠并拖动调宽 | 用户按任务密度调整项目内导航和内容比例 | 双侧栏拥挤、长标签、宽度上下限及偏好恢复；拖动之外需要按钮/键盘替代；自定义模板不宜各自实现不一致的管理导航 |
| 平台窄栏＋显式展开/固定，项目导航按需收起 | 作为当前优先打样的组合；全局入口可发现，内容区域较稳定 | 仍需比较管理兜底、普通业务和全屏三种模式，自动收起的触发范围及恢复规则尚未定案 |

当前推荐先比较第三种组合与两种原始候选，复用同一真实平台外壳和同一项目内容。悬浮可以成为快捷操作；显式按钮、键盘和触屏入口必须存在。项目导航拖动宽度先验证确有收益再纳入首个增量；可折叠与合理固定宽度可以先满足基本需要。职责明确不意味着增加一层必经页面或增加业务对象层级。

实现约束：优先在现有 `AppLayout.vue`、`ProjectDashboardView.vue` 及导航状态 Owner 处理布局联动。用户手动折叠偏好与进入 Dashboard 的临时呈现分开；退出或返回时按明确规则恢复，不能反复覆盖偏好。自定义页面通过宿主认可的布局模式或事件协作，平台执行状态变化；Agent 页面不得直接操纵平台 DOM、全局路由或导航存储。是否需要跨 frame 消息按最终加载机制决定，不提前建立通用桥接框架。

下一轮至少给出桌面管理兜底、桌面业务大屏、平台导航悬浮/固定展开、项目导航收起/调宽、窄屏和全屏返回六种状态的组合页面稿。核对真实可用宽度、滚动归属、遮挡、长名称、焦点及展开入口，而不是仅在孤立 Dashboard 中测试。

专项收尾必须证明：平台→项目→Dashboard→准确结果→返回原观察位置，跨项目切换不串身份；展开、固定、折叠、离开与重入的状态按决定恢复；菜单操作中不误关闭；键盘/触屏可操作；模板失效或业务页出错仍能回管理兜底。与 Agent 大屏及模板的实际宿主集成必须覆盖这些规则。缺少平台嵌入验证时，允许独立产品增量推进，但不能宣布信息架构与 Dashboard 专项整体完成。
