## 任务背景与目标

在元垒测试中，用户发现模型实际最大输出只有 4096 token，长任务生成被截断并中断执行。为临时缓解，在 `backend/package/yuxi/models/chat.py` 的 Anthropic 分支加入了 `kwargs.setdefault("max_tokens", 65536)`。该改动已包含在 `6a672f4d7029bb3bd84209d6c70d46dd4bc56980`。

请基于 `develop-v0.0.1` 的当前实际代码完成修复及收敛，遵循仓库规范、保留已有用户修改，不回退工作树到旧节点。目标是找到实际限额来源，让当前受影响模型使用明确、可维护且有效的输出配置，并使真正的输出截断得到正确识别和处理。完成实现、相关测试、必要工程记录和独立 Review，交付具体结果。

这是一项聚焦修复。先自行调查并选择满足目标的最小方案，简短说明后推进；只有确需用户才能确定的模型身份、配置变更或业务语义才集中询问，不为了参与感逐字段提问。

## 1. 先定位真实原因

沿实际运行路径核对：模型配置保存与归一化→Redis/ModelInfo→API/worker 加载→Agent 及 middleware 参数→供应商 SDK→最终请求参数→响应结束原因→AgentRun 结果。普通聊天与 Agent 工具执行实际使用的入口需分别确认。

已知入口包括 `load_chat_model`、`select_model`、`_langchain_kwargs`、providers service/cache，以及真实 Run 终态和消息输出 Owner；不要仅修一个调用入口后假设所有路径相同。

保留用户关于 4096 截断的观察，读取能取得的去敏运行证据。区分单次模型生成上限、输入上下文窗口、Agent 步数、超时、任务累计 token 以及用户预算，确定本次中断属于哪一种，不把所有问题归因于同一个 token 数值。

补充调查事实：2026-10-09 的本地 API 容器中，`ChatAnthropic.model_fields["max_tokens"].default` 回读为 `None`，因此尚不能把当前安装 SDK 字段默认值直接认定为 4096。仍须核对 SDK 实际参数构造、供应商/代理默认限制及出问题时的版本和调用路径。这不是对用户观察的否定。

当前 `ModelInfo` 没有独立输出限额字段；模型发现逻辑虽出现 `max_completion_tokens`，需确认是否只是展示信息，是否进入归一化、保存、缓存和实际请求。`request_body_overrides` 当前限定 OpenAI 兼容供应商，不能未经兼容判断拿它解决原生 Anthropic 参数。

## 2. 修复输出参数的真实传递链

优先使用现有模型配置机制；确实缺少有效配置时，在真实配置 Owner 增加最小字段和输入校验，贯通必要的保存、缓存、API/worker 读取及 SDK 装配。若现有设置页面没有可用入口，补该字段的必要设置及说明即可，不重做模型管理界面或建设新配置系统。

明确三个不同概念：供应商允许的最大输出、项目配置的默认输出上限、本次调用显式指定的输出上限。可采用“调用显式值优先，其次模型配置默认值，最后有依据的协议/SDK 默认”的规则；必须核对现有配置语义，避免改变已经使用的覆盖顺序。模型最大能力用于合法性判断，不自动等于每次请求的默认额度。

按真实协议装配正确字段，验证当前 Anthropic 路径及受影响的通用入口；其他协议仅做必要兼容回归，避免全供应商重构。同一请求不能含互相冲突的输出参数；显式较小限额必须保持有效。参数不合法时给出明确错误，已有合法配置不因新增字段意外失效。

对实际受影响模型，根据真实支持范围配置足够的默认上限，不能把未知模型能力猜成 65536，也不能将所有模型统一改成该值。已有配置迁移只触及必要对象，保留可解释的默认与回退行为，API 与 worker 最终生效值一致。

不要先删除临时配置再让缺陷回归。完成替代配置及回归后，移除全 Anthropic 分支硬编码，或根据明确理由将其收敛到准确适用范围；同时清理该行附近的尾随空白。不得以删除配置、重新落回短输出默认作为修复完成。

## 3. 正确处理仍然发生的截断

提高限额不能保证每次生成都完整。检查流式和非流式路径是否保留供应商结束原因，关注截断信息是否在适配器、消息合并或 SSE 中丢失。

Anthropic 的 `stop_reason=max_tokens` 表示本次输出达到请求上限；正常 `end_turn`、合法 `tool_use` 和上下文窗口耗尽须分别识别。官方说明也指出截断可能造成不完整工具调用，应在实际调用边界处理。[官方结束原因说明](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)

复用已有恢复/错误语义：若现有流程能安全继续，应保留截断事实并按已有有界机制继续；若不能，保留已生成内容和可恢复位置，返回明确的输出截断信息，并在实际任务界面给出必要提示。截断的最终输出不得静默冒充完整交付或导致工作自动完成，部分工具参数不得被执行。不要求所有内部截断响应一律终止 Run；看它是否经过合法恢复以及最后是否形成完整交付。

本次不建设通用自动续写系统，不无限提高限额或无限重试，不从头重放可能已经产生副作用的工具任务。尤其确认：配置修复能防止原来的过小限制；遇到新的真实上限时系统能准确说明，用户不会看到无声中断或假成功。

## 4. 验证与验收

使用有意义的相关测试，按风险补真实数据库/HTTP/Run 链路验证：

1. 明确原始故障的限额来源及生效路径；若历史现场不足，区分已证实原因与待实测部分，不能只写“默认 4096”。
2. 模型默认值保存、缓存、重新加载后进入真实 SDK 请求；Agent 与普通调用入口均使用正确优先级。可用受控 HTTP 接收端核对最终参数，而非只检查中间 Python 对象。
3. 较高合法限额、显式较小覆盖、未配置的旧模型、非法配置及已知模型上限等案例成立；证明配置不会回落到意外短输出，也不输出冲突字段。
4. 流式和非流式的长合成响应不会被应用自行按 4096 截断；供应商限额截断、正常结束、合法工具调用及不完整工具参数有不同结局。
5. 对受影响 AgentRun 回读持久状态、部分输出和结束原因，证明截断没有被默认为完整交付，恢复不重复工具副作用。权限、预算、取消和既有完成语义保持有效。
6. 有真实模型环境且授权范围允许时，使用有界合成输入复测原问题；无需为证明限额传递消耗完整 65536 输出。真实调用未执行时说明原因和剩余验证，不用 mock 宣称真实模型已经通过。
7. 运行适用工程检查与独立 Review，修复本次产生的问题；旧有无关失败分开记录。不要顺带改其他专项或历史业务结果。
