## 3. Dashboard 会话：有效调查之后，设计推进过于零碎

### 3.1 应保留的工作

会话区分了可信默认 Vue 页面和受限静态 HTML 自定义页面，没有把未来 Vue 生成能力说成已经存在。它识别了管理与业务大屏的切换缺口、已读与已处理的区别、结果份数与工作数的区别，以及交付文件路径和历史完成状态的展示问题。

用户明确授权后创建隔离测试项目，完成了人工工作、文件提交、待验收定位、预览、接受和完成的真实操作。它也没有把这个单结果样本泛化为智能体自动导入、并发、多结果或收件箱已通过。这些证据值得保留。

### 3.2 具体问题

| 会话中的做法 | 问题 | 应怎样推进 |
| --- | --- | --- |
| 让用户从三条走查路径中选择 | 路径是覆盖计划，可以自行排序；三条都重要，首条选择不应变成缩小专项范围 | 给出推荐顺序和各条要验证什么，只有样本或访问条件不足时问用户 |
| 询问第一眼看五类信息、直接定位结果或先看工作全貌 | 把信息内容、进入路径和布局混成互斥选择；没有展示各方案如何处理同一场景 | 先定义办理所需信息，再比较完整工作详情方案 |
| 结束时询问内嵌预览还是新标签 | 缺少文件类型、长文阅读、屏幕尺寸、工作条件对照和实现成本；可组合的方案被压成二选一 | 对比页内摘要、可展开预览、大文件独立打开的组合及替代方案 |
| 获得一次局部选择就写成 U1 要求，然后继续问下一处 | 缺少与全系统信息层级、模板和项目专属大屏的连接 | 每次确认更新整体方案，说明影响哪些页面、验证什么和下一步做什么 |
| 问题地图有全局内容，下一步却继续单点询问 | 日常体验和 Dashboard 生成基础之间失去共同主线 | 下一轮同时交付跨页面候选方案和生成能力研究路径 |

“工作标题、结果摘要、验收条件、交付文件、办理按钮”是合理要求。应表达为：进入办理位置后，用户无需失去工作身份或另行寻找依据，即可理解当前交付并作判断。验收条件可先展示关键摘要并展开提交时快照，文件可先呈现列表及预览入口；长正文不必全部铺在首屏。

### 3.3 不能让局部观察代替专项目标

单次人工验收检查不能覆盖项目工作台、收件箱、智能体工作台、深浅主题、密集数据、错误状态和项目业务大屏。也不能回答素材库、模板库、智能体创作、动态数据和发布机制怎样建设。下一轮需要补齐场景覆盖，但每个状态无需都由用户陪着点击。

可以先按“日常管理及办理体验”和“可复用 Dashboard 能力”两条相互衔接的研究线组织方案。默认管理仪表板是样板，项目专属大屏是实际消费者；两者共同验证数据、导航、布局素材和异常兜底。

### 3.4 产物内部还存在未同步的进度表述

U0/U1 第 95 行仍写“当前等待用户反馈结果办理首屏的信息需要”，第 127 行已经记录用户确认。第 25 行的“没有……执行验收”属于登录阶段观察，但没有明确限定该阶段，后面的第 111 行已经记录实际验收完成。第 83 行“实际 DOM 尚未验”也需要收窄到尚未覆盖的多结果等场景。主规划第 187 行笼统写“尚待用户业务页面操作补齐”，没有区分已走通与未覆盖路径。

这不否定实际操作证据，却说明文档在追加记录后没有统一当前状态。下一轮应更新相应摘要和问题地图，保留必要历史及证据，不能仅在末尾继续追加一段。否则后续会话可能反复要求已经完成的反馈与验证。

## 4. 协作会话：事实摸排有价值，下一步需要从例子进入方案

### 4.1 应保留的工作

会话发现实际服务、本地检出和旧评估版本不同，区分了健康响应、发现能力与执行就绪。指定工作区的一项 issue 有五次运行，直接说明只绑定 issue 不足以取得当次交付。OpenClaw 的 CLI 与 Gateway 版本交叉核对也有价值。

它指出元垒已有委派、子运行、恢复和验收基础，同时明确本地子运行当前只有一层。正式批准工具、限定授权、跨平台求助与准确恢复尚未实现，没有用完成 announce 或 HTTP 成功冒充 Andon。

工作区选择是合理的范围澄清。用户登录和新建测试项目涉及访问或写入条件，也属于合理请求，不能和缺少设计判断的提问混为一谈。

### 4.2 尚欠缺的产出

| 缺项 | 为什么重要 | 下一轮补什么 |
| --- | --- | --- |
| 完整委派及 Andon 路径的候选方案 | 身份、问题、回复、恢复和验收相互影响，单个例子不能替代总体方案 | 用同一场景对照多条真实接入路径，说明可承诺的闭环 |
| 授权方式的明确推荐及边界 | 已列一次授权、有限类别授权，但没有说明现阶段采用顺序 | 比较操作频率、范围可核查程度、撤销和实现成本，给出推荐组合及反证条件 |
| 能力差异的产品后果 | 大量未验项没有转成“若不支持，如何使用” | 标明原运行续接、新尝试和仅通知模式各自的体验与限制 |
| 哪些未知会阻塞哪项研究 | 完整构建 SHA、最小权限、输出关联的影响不同 | 分开可继续研究、试验前需补、产品承诺前需证实的项 |
| 已知缺陷的独立处置路径 | 首轮记录把修复放 C5，容易等整个专项定案才处理 | 单列缺陷修复候选；不依赖整个新框架的修复可先给具体方案，但实际实现仍需对应任务授权 |

“已批准资料写明统一含税，直接上级在范围内回答”是既定原则的应用，不值得单独问用户是否可以继续。需要核实的是资料是否具有约束力、问题是否同一口径、执行者是否采用了答复。

“三年改两年”只有在三年是正式批准的约束时才走正式治理变更。如果是资料整理的暂定方法，应由执行委派范围判断。场景要标清前提，再解释系统如何处理，不能让用户通过一个数字例子重新定义整套权限。

## 5. 原规划的推进规则也需要纠正

原启动文本正确限制了直接改代码、预定框架和一次性实现，却没有明确要求：讨论前必须交付充分分析，候选必须同尺度比较，Codex 必须承担推荐责任。

原 U0/U1 的推进条件又强调用户操作校准，容易被执行为“每一处都等用户确认才能研究下一处”。应补充：已明确边界直接继承；局部未知可作为显式假设；对影响较小、可逆的研究选择给出建议后继续；真正影响范围、权限、业务判断或难以撤销的决定再等待确认。

U0/U1、C0/C1、比较和试验是产出检查点，不要求机械地全部串行。可以带着不确定项形成候选方案，并用试验解决分歧。研究建议可以明确，正式决定仍需具备充分证据和适当授权。两者不冲突。

仓库要求证据分级、Decision、独立 Review 和文档检查本身有价值，本次不建议关闭。设计充分性还需要单独审查：问题是否完整、方案是否同尺度、推荐是否有理由、用户选择后是否能看见建设路径。文档构建与既有文风检查不能承担这项职责。

## 6. 两个会话统一采用的工作方式

### 6.1 每轮交付一个能推进整体设计的成果

依次说明：本轮解决的问题、已经明确的约束、相关证据、完整候选方案、推荐及理由、采用后的工作安排、尚需用户判断的分歧。没有实质分歧时直接提交成果，不为保持参与感制造问题。

未知项同时写明负责补齐者、验证方法、影响哪项判断、验证失败后的替代路径。仅写“后续确认”无法指导工作。

### 6.2 讨论前提供充分选择信息

比较应覆盖同一组场景和边界：用户怎样操作、各模块怎样关联、所需数据和能力、失败怎么办、建设及维护成本、兼容影响、分批实施顺序。技术方案和交互方案可以分层组合，不强行捆成三个大礼包。

不使用只有外观差异的三套皮肤，也不为凑数量发明劣质替代。真正有多个可行方向时比较；明显优于其他方向时给一个推荐和可信反对理由。

### 6.3 用户负责目标和重要取舍，Codex 负责研究和设计

| 问题类型 | 处理方式 |
| --- | --- |
| 已确认原则，例如扁平项目、直接上级优先处理、可选过程补充 | 直接继承，核对适用前提 |
| 常规布局、走查顺序、原型组织、研究范围内的可逆方法 | 给推荐、记录假设、继续工作 |
| 用户独有的业务事实、实际目标、可用实例、必要访问条件 | 询问缺失信息，同时推进独立工作 |
| 批准权限、业务范围改变、实际外部任务、正式发布等 | 先完成可审阅方案，再按已有授权判断是否需要确认 |

重要问题需要写出：为什么需要用户判断、完整替代及利弊、推荐、采用后的影响、现在不定是否阻塞哪项工作。按真正关联的决定成组讨论，不把整个方案拆成十几次小问答。

### 6.4 用户选择之后必须返回更新后的完整方案

不要只说“已记录”。说明哪些章节、原型、协议或实现顺序发生变化；哪些既有约束仍成立；哪些风险需要试验；下一轮的具体产物与验收方式是什么。

## 8. 继续原会话还是重开

首选继续原会话。完整发送配套纠偏指令，明确停止当前零碎提问，继承事实，重构设计任务。不要再先回答文件预览二选一或含税例子。

下一轮若仍然只有问题清单、原规划复述、没有完整对比和推荐，就重开相应会话。新会话使用同一纠偏指令，读取主规划和可保留事实，不继承聊天里未经充分分析的局部选择。是否重开不改变代码事实，也不需要删除旧研究记录。

| 下一轮检查项 | 合格表现 |
| --- | --- |
| 是否覆盖整体目标 | 同时处理主要主线及接缝，没有继续缩成一个按钮或一个例子 |
| 是否承担设计判断 | 有明确推荐、淘汰理由和会改变推荐的证据 |
| 是否可知选择后果 | 能看见用户路径、能力影响、分批建设和验证顺序 |
| 是否保留真实边界 | 未验不冒充支持；研究建议不冒充用户决定；第三阶段内容没有前置 |
| 是否减少无效参与 | 问用户的是实质业务与授权分歧，常规研究判断自行完成 |
