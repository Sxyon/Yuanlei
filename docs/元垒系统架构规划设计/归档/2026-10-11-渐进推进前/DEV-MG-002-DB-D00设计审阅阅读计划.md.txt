# DEV-MG-002｜DB-D00 设计审阅阅读计划

读者：用户与设计执行者。用途：按整体目标、页面逻辑、架构机制、实施覆盖的顺序审阅 Dashboard 设计。前置材料为当前 SYS/DEV/LOG 和已校验图稿；本页只导航阅读与反馈，不拥有设计或进度。需求修改回写 SYS，确认及推进事实记录在 LOG。

## 1. 先理解整条主线

元垒平台外壳 → 进入项目 → 管理概览或项目业务大屏 → 看议题的当前结论与关联行动 → 进入准确工作和交付办理 → 返回原观察位置。项目业务大屏的另一条主线是：选择模板或组合素材 → 创建项目实例 → 绑定数据 → 保存草稿 → 验证预览 → 启用 → 设首页 → 后续修订与回退。智能体消费同一套规则和工具，在明确范围内维护。

前一条主线解决日常管理体验，后一条解决各项目自己的观察页面。它们共用平台外壳、项目身份和准确对象导航，但各自保留职责。先判断这两条主线是否满足预期，再核细节。

推荐分三次审阅：第一轮审目标与日常页面；第二轮审模板、生成、数据和维护；第三轮审开发覆盖与验收出口。每轮可安排约20—30分钟，实际以形成判断为准。各轮结束由执行者归纳意见、修订设计并说明影响；用户无需先读完全部文件，也无需操作原型才能提出意见。

## 2. 第一轮：整体范围与日常页面

### 第一步｜先看当前事实，再看整体目标

先读 [LOG-DB-001 第2、3、5节](LOG-DB-001-Dashboard进度基线与执行记录.md#_2-已实现能力与证据范围)，只建立“已有、待验、待开发”的区分。随后打开 <a href="图解/01-platform/platform-target.html" target="_blank" rel="noopener">PL-G01 系统目标图</a>，配读 [SYS-PL-001 第2、5节](SYS-PL-001-系统架构与阶段边界.md#_2-核心对象与职责)。历史轮次报告按需查证。

重点判断：项目是否仍为扁平业务空间；议题、决定、工作、结果的职责是否清楚；团队治理留第三阶段是否保持；周期/自动化统一和暂停 Andon 是否被明确留在对应后继范围。目标图表达规划关系，图上有节点不代表代码已实现。

本步产出：保留整体边界，或指出某个概念和阶段划分需要修改。无需批准任何产品实现。

### 第二步｜平台、项目与页面职责

读 [SYS-DB-001 第1—4节](SYS-DB-001-Dashboard系统需求与架构设计.md#_1-产品定位和范围)，第3节的页面职责表是重点。对应 <a href="图解/02-dashboard/dashboard-architecture.html" target="_blank" rel="noopener">DB-G02 Dashboard 架构图</a>中的宿主、管理与业务展示区域。

逐项核对：

- 平台导航、项目导航、页面内锚点是否各管一层，内容可用宽度是否足够。
- 管理概览优先告诉人“什么需要处理”；业务大屏优先展示项目数据，两者切换与管理兜底是否始终可达。
- 工作台、工作列表、工作详情、收件箱、项目 Agent 是否各有清楚职责；同一结果从不同入口打开时是否到同一个准确办理对象。
- 全屏、窄屏、长文、返回、切项目时，人是否仍能判断自己在哪里。

当前推荐是平台窄栏＋显式展开/固定、项目导航按需折叠。收益是入口稳定、键盘可达；代价是保留一定常驻空间。悬浮作为唯一入口容易出现发现和焦点问题；可把悬浮作为补充。拖动宽度带来更细的个人适配，同时增加宽度保存、最小内容宽度和窄屏行为；若真实布局证明固定宽度频繁妨碍阅读，再引入。

本步可以判断导航方向与页面分工。具体空间比例、密度和视觉质量须结合完整外壳草图；架构图不足以批准最终排版。

### 第三步｜议题一体详情：逐模块审，而非逐按钮审

打开 [SYS-DB-002 的整体编号草图](SYS-DB-002-议题详情设计审阅示范.md#_1-目标、整体与阅读顺序)，再看 <a href="图解/05-topic/topic-relations.html" target="_blank" rel="noopener">DB-G05 模块关系图</a>。按下表顺序读局部说明，每个模块先判断理念，再看操作和状态。

| 阅读顺序 | 对应章节 | 审查重点 |
| --- | --- | --- |
| M1 身份与约束 | 第2节 | 项目、议题、状态和暂停提示能否立即辨认；常用动作是否易找 |
| M2 问题与目标 | 第3节 | 先读问题和方案再编辑是否自然；问题型与推进型议题是否都能表达 |
| M3 当前结论 | 第4节 | 多项有效决定与补充/替代是否清楚；草稿、当前、历史能否区分 |
| M4 关联行动 | 第5节 | 能否看懂结论如何落地，进入准确工作/结果并回来；独立工作仍可存在 |
| M5 讨论与变化 | 第6节 | 是否像持续论坛主题；最新讨论、回复、修订与批准节点能否理解因果 |
| M6 材料与规则 | 第7节 | 证据容易找到且正文不拥挤；规则和文件仍引用真实来源 |

推荐同页维护议题、讨论、决定入口，以当前内容和结论为主线，历史渐进展开。数据对象仍分别维护，以保留正式批准、修订、替代和准确执行依据。将任务接受等办理留在工作详情，代价是一次跳转，收益是所有入口使用同一套办理语义与权限。

布局比较重点看第8节：主阅读区＋侧栏便于同时定位材料，代价是正文变窄；全文单列＋抽屉让长文更舒适，代价是查看证据需要额外展开。当前候选推荐前者，长正文和窄屏实测可能改变选择。

用三个故事检验布局：研讨中尚无决定；批准后已有工作和交付；重开且暂停原方案。再补一例旧条件结果，看人是否会误认为它适用于最新方案。正式状态稿、接口映射和布局对照尚需补齐，现有示范可用于提出意见，不能当作完整 DB-D00 已交付。

## 3. 第二轮：项目自定义大屏的规则与闭环

### 第四步｜先核谁管理什么，再核生成方式

读 [SYS-DB-001 第5、6节](SYS-DB-001-Dashboard系统需求与架构设计.md#_5-自定义大屏的对象模型)，沿 DB-G02 追踪“素材/模板 → 定义草稿 → 验证 → 生效修订 → Runtime”。

重点判断：模板是可复用结构，实例属于项目；同模板可派生多个实例，各项目独立绑定；模板升级先产生草稿；预览、启用与首页选择分开。页面定义与关系放数据库，文件作为受授权来源或导出，不让共享目录成为项目身份。

首阶段推荐受控结构组合＋可信 Vue 素材。Agent 选择布局、组件、参数和数据映射，由产品 Runtime 加载。收益是规则可发现、验证与加载统一；代价是表达受组件能力限制。任意生成 Vue 更自由，但需要额外编译、依赖、资源隔离和宿主交互维护。出现受控方式无法表达的具体业务样板，且扩充素材也无法合理解决时，再审隔离 Vue 路线。

本步请判断这种创作自由度是否满足第一阶段目标。执行者需用“交付观察”和“经营观察”两个具体页面解释可表达范围，不能只让用户抽象选择技术路线。节点/字节预算由开发负控校准，用户无需逐项审批数字。

### 第五步｜数据怎么来，点击后怎么走，Agent 怎么维护

依次读 [SYS-DB-001 第7—9节](SYS-DB-001-Dashboard系统需求与架构设计.md#_7-数据、分析和资产)，仍配 DB-G02。

| 核对链路 | 必须回答的问题 | 推荐及代价 |
| --- | --- | --- |
| 数据来源 | 正式工作事实、项目业务数据、分析观点如何区别；缺数/失权怎么显示 | 数据与页面各自版本化，页面回退不回滚业务数据；需解释历史页读取 current 的含义 |
| 点击与返回 | 大屏点某个结果进入何处；办理后如何回月份、筛选、修订和位置 | 注册动作进入可信办理页，宿主校验并保存返回状态；增加一次跳转及返回机制 |
| Agent 创作 | 规则从哪里发现，生成物在哪保存，错误在哪修，谁启用 | 工具与页面共用服务，候选→验证→预览→人工启用；自由创作增加一次人工启用 |
| 有限维护 | 哪些变化可自动生效，越界和撤权如何处理 | 固定模板明确授权内自动维护；布局授权与数据采纳授权分开，需要两类清楚的政策说明 |

本步请判断人工启用与有限自动维护的边界、数据采纳方式和返回体验。接口命名、数据库字段、令牌实现由执行者负责。启用 Dashboard 不包含批准正式决定或恢复暂停协作的授权。

用同一连续故事审查：从模板派生项目大屏→绑定数据→Agent 修改→预览→启用→点结果办理→返回→模板升级失败→稳定页仍可用→回退。缺任何一段的页面稿或说明，记为待补设计材料。

## 4. 第三轮：开发有没有覆盖设计，最后怎样验收

最后看 <a href="图解/03-dashboard-tasks/dashboard-tasks.html" target="_blank" rel="noopener">DB-G03 开发任务图</a>，读 [DEV-DB-001 第1节和 DB-D00](DEV-DB-001-Dashboard开发任务与实施约束.md#_1-开发组织和顺序)，然后读 [SYS-DB-001 第10节](SYS-DB-001-Dashboard系统需求与架构设计.md#_10-独立验收场景与收尾标准)。任务卡只按需展开。

审查顺序为日常办理 T01—04 → 动态基础 T05—07 → 业务数据 T08 / 模板多实例 T09 → Agent 生成 T10 / 有限维护 T11 → 故障及连续验收 T12—13。图中箭头拥有精确依赖；这一阅读顺序不要求所有包串行。

重点检查每个已认可设计都有任务和可观察出口；模板不因等待全部数据能力而被阻塞；Agent 页面生成和数据候选分批；阶段结束有可用结果；收尾同时包含治理、业务大屏和真实 Agent 链。协作保持暂停，Dashboard 展示未接入状态。

DB-D00 结束可以得到分项确认：整体职责、某一页面组织、动态创作路线、数据/维护边界等。实施从已确认且设计材料齐备的范围领取，确认消息和稿版本记录在 LOG。完整 DB-D00 的材料和判断全部齐备后才能登记完成。

## 6. 怎样反馈，怎样收敛

直接用模块号和场景表达意见即可，例如：“M3：我希望先看到有效结论，草稿默认折叠”“模板管理：先看项目所有实例，再进入库”“返回：我需要保留月份，不要求恢复全屏”。也可以只描述感受和预期；执行者负责转成准确设计变更。

每轮执行者归纳：对应图/模块与版本；用户判断；推荐如何调整及影响；待补材料；已明确确认的范围。修订回写 SYS，真实确认进入 LOG。对多个模块有影响的反馈先更新整体关系，再更新局部稿。

第一轮建议从第二节开始：先约定整体范围与页面分工，再集中审 M1—M6。用户可分项保留、修改、暂缓；单项反馈不自动表示整个专项或后续开发全部获批。
