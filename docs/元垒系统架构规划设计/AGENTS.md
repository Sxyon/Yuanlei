# 专项管理文档约定

- 当前入口由[目录README](README.md)拥有；归档只供历史追溯，不领取其中旧任务。当前SYS/DEV/LOG在本目录维护，图解与回执在图解目录。已吸收过程移除，精确历史由Git追溯。
- 专项任务先读[推进与设计汇报机制](DEV-MG-001-专项推进与设计汇报机制.md)，再读该任务的SYS/DEV/LOG；读取当前源码重建实际状态。
- SYS拥有需求、系统设计和取舍；DEV拥有实施包及技术约束；LOG拥有实际状态、用户确认依据、执行反馈和证据引用。按类型-专项-三位编号命名，修订同职责文件，不另造并行主规划。
- 设计变化先说明整体位置、模块理念、替代比较、推荐和风险；布局稿按需，关系图依下条触发，已有有效稿可引用。保留已有产品；未确认新设计时仅做隔离稿及独立已授权准备。
- 完整稿覆盖当前阶段及其上下文，远端只保留目标与验证时机；调研/小试先于技术定案。阶段末细化下一段，关键假设失败或用户新方向随时中断受影响路径并重审，不要求全部远期设计预批准。
- 仅需对架构／关系／流程／状态做取舍判断时使用Archify；关系未变复用，日常进度轮不画。按需读取技能、交付校验HTML及证据，页面布局另备。
- 确认依据记录原用户消息/会话和对应稿版本、范围；Agent建议、Reviewer通过、无回复和原型操作记录不能冒充用户确认。
- 每轮先报目标与变动，再报实现和证据。开发完成列人工验证路径及可观察结果；反馈修完并获人工验收后才做全量测试，验收前仅相关检查。状态与否决条件见推进机制。
- 日常用进度/问题/计划，关键选型用现状/问题/方案/建议/请示；具体案例、推荐和证据齐备再交用户判断。
- 主题专项阶段暂停，协作接入与Andon保持暂停，恢复须用户明确指令。管理文档调整不授予外部试验或正式业务权限。
